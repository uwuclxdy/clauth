# Interface and keys

`clauth` opens on the Overview tab. <kbd>←</kbd> <kbd>→</kbd> or <kbd>tab</kbd> / <kbd>⇧tab</kbd> move between tabs at the top level, and <kbd>⌥1</kbd>–<kbd>⌥9</kbd> jump straight to a tab. While a detail pane has focus the arrows are trapped: <kbd>←</kbd> returns to its selector and <kbd>→</kbd> does nothing there. <kbd>tab</kbd> / <kbd>⇧tab</kbd> still switch tabs from a descended read-only detail (Usage, Tokens model, Services `delegates`, or Status) and do nothing in a descended editable pane. <kbd>?</kbd> lists every binding for the tab you are on; <kbd>q</kbd> twice quits from the top level.

## Tabs

| Tab | Holds | You can |
|-----|-------|---------|
| **Overview** | account table, live 5h / long-window bars (7d, or Alibaba's monthly quota), chain position, selectable codex and pool accounts | switch or reorder Claude Code accounts, browse codex and pool accounts, refresh or remove a pool account, pick which harness shows |
| **Usage** | per-account window breakdown for every Claude Code, codex and shunt pool account: 5h, 7d, per-model weeks, extra-usage spend, peak-rate state; a codex or pool account shows its own facts and windows | refresh one Claude Code account or re-read the pool listing, toggle estimates and the pace marker (Claude Code panes), edit a Claude Code account's note |
| **Tokens** | global Claude Code token stats and API-equivalent cost | drill into models, move between dashboard cards, change the period lens, count cache tokens |
| **Setup** | the Overview's account list (Claude Code, codex and pool rows), then each Claude Code account's endpoint, key, env, model routing, auto-start, 5h alert | edit any of it, log in, log out, disable or delete a Claude Code account, create a claude, codex or pool account, re-login or delete a codex account, refresh or remove a pool account |
| **Fallback** | the auto-switch chain | reorder members, edit thresholds, flip gates, set a spend ceiling |
| **Config** | program-wide settings | change any of the rows in the table below |
| **Status** | incidents from status.claude.com with per-component health | open an incident's timeline or its page in a browser |
| **Services** | the shunt gateway, running delegates, the Claude Code plugin and herdr | apply fixes |

The active account is orange. A `▲` on an account's row means the provider behind it is on peak-rate hours right now — some providers charge more at set times of day (DeepSeek roughly doubles its API rate; Z.ai's GLM peak hours consume the coding plan's quota faster). The active account's mark sits in the marker column, in orange: `✻` on a claude account, cycling `· ✢ * ✶ ✻ ✽` and back (Ghostty draws its own set) while that account is spending tokens; `⏣` on a codex account; `⥋` on a claude account holding a shunt gateway client token. The mark outranks `▲` on its own row, so an active account on peak hours keeps its mark and `▲` shows on the other accounts. A red `!` marks an account whose 5h alert fired, until its usage falls back below the line, and it outranks the active mark. The Usage tab's `pricing` row names the state, the countdown to the next switch, and nothing renders for flat-rate accounts. The marker follows the provider's own published rate schedule, never which models the profile pins; an account on an endpoint clauth doesn't recognize shows none. A codex account's banked usage-limit resets show as `↺ N` on its Overview row while one is available — `clauth limit-reset` spends one ([Codex](Codex#use-a-usage-limit-reset)). Usage numbers are cached on disk, so they stay on screen when the API is rate-limited or unreachable. Once those figures age past the refresh cadence's stale threshold, the Usage tab's status block adds a `[ stale ]` pill; it reads the age of the reading — an OAuth account's own fetch stamp, one it cannot date reading stale at once, or a third-party account's cache write time — not the last fetch outcome, so a `[ cached ]` pill and it can appear together. An amber `⋯` in place of the refresh countdown marks a cached reading clauth no longer polls. On the fallback chain panel below the accounts, `↲ ~40m` beside a member names the account the chain switches to next, and roughly when. When the panel is too short to show every member, its last line reads `+N more · → fallback tab`: N members are off-screen, and the Fallback tab, four tabs to the right (<kbd>→</kbd> or <kbd>tab</kbd>), lists them all.

An account's `t/s` column sits after `live`: its live speed, blank where the producer carries none, dropped whole first on a narrow terminal, before the 7d reset stamp sheds a cell, and given up to the wall-clock reset stamps when `reset_display` is `clock` or `both` and both do not fit. The Usage detail lists `speed` and `rate` rows under its header: the `speed` row reads `live · 5m · 1h · today · peak` and the `rate` row `live · 5m · 1h · today` (speed = output ÷ generation time, rate = output ÷ window length): a rate reads `0` under a fresh producer when the account spent nothing, a speed reads `—` when no response touches its window, and every figure reads `—` while no fresh producer stands behind the cache. The Tokens tab's today card carries a `speed` row (`S t/s now · S t/s today · S tok/s peak`), the TOTAL card an `avg speed S t/s · S t/s peak · S tok/s peak` row once a day of speed history exists (what each peak means: [Tokens and cost](Tokens-And-Cost#token-speed)), and the trend chart a speed strip under its bars with `· avg S t/s` on its caption — the strip drops before the month ticks on a short card. The Services `delegates` detail lists `S t/s` among a job's facts: a running job's live speed off its own session, a finished job's own average.

Codex accounts ([Codex](Codex)) sit under the Claude Code rows in a section headed `codex`, in the same columns: name (bold, in the blue accent, when it is the active codex profile, with `⏣` in the marker cell), plan, 5h and 7d, with `—` where nothing is cached, and a dim `↺ N` after the columns while the account holds a banked usage-limit reset ([Codex](Codex#use-a-usage-limit-reset)). The rows are selectable: <kbd>↑</kbd> and <kbd>↓</kbd> reach every codex account, including the last one in a short viewport; <kbd>⏎</kbd> does not switch a codex account, and <kbd>a</kbd> opens tab-wide actions without an account group. There is no live, t/s or timer cell. A codex row shows the same `×` marker when its chain is quarantined, and its plan cell falls back to the plan the account's login claims while no poll has cached one. The accounts panel title carries the active filter — plain `ACCOUNTS` unfiltered, `ACCOUNTS ─ claude` / `ACCOUNTS ─ codex` / `ACCOUNTS ─ shunt` filtered, the harness name in dim text (the border rule supplies the dashes) — and its right edge shows the by-harness counts (`52 claude · 1 codex · 4 shunt`, an empty roster's harness omitted), the first thing to go on a narrow terminal. The header's line 2 opens with `[ N live ]  [ R tok/s ]`, then holds the gauge with its speed suffix and the status dot: `N live` is every live session clauth can see, whatever account it runs on, split as `[ 6+7 live ]`: the end user's own sessions first, then `clauth mcp` delegates in the blue accent, with a dim `+` between the parts (a zero part drops with its `+`, so delegates alone read `[ 7 live ]` in blue; both zero read dim `[ 0 live ]`, and `[ — live ]` when clauth cannot read where it tracks them); `R tok/s` is the fleet's live token-consumption rate off the speed cache, dim at `0` and at `—`, the latter while no fresh producer stands behind the cache; the gauge carries the active account's live speed as `(S t/s)` (dim, absent when the gauge is or when the account has no fresh live speed). A narrow terminal drops the tok/s chip first, then the live chip, then the speed suffix, then the gauge's own ladder, then the status dot.

Shunt pool accounts sit after the codex rows, one `shunt (<provider>)` heading per provider with a row per account under it. A row shows the account name; the plan in the type column (`—` where the gateway reports none); the 5h and 7d bracketed bars with their reset countdowns, `—` where the gateway reports none; and blank live and t/s columns. Status rides cues: a red `×` before the name when the account needs a re-login (a spinner takes its place while a pool action runs on the row), a dimmed row while it is paused or disabled, a cooldown's remaining time in the timer slot in amber, and the bars' threshold colors as it nears its quota. The `codex` heading and each `shunt (<provider>)` heading are dim and bold, and brighten while the cursor rests on a row under one. A listing clauth cannot read shows one `shunt — not read: <reason>` heading and no rows; with no gateway adopted, a config without clauth's admin entry, or a missing admin token file, the section does not appear: the Services card offers `f  add admin table` or `f  add admin key` for a missing table or entry, and while the gateway runs it reads `pool  no gateway admin token` for a missing file.

The Usage tab lists the same accounts as Setup, unfiltered and without `+ new`: the Claude Code accounts, then the `codex` section, then one `shunt (<provider>)` section per pool provider. A codex account's detail shows `type  codex`, its plan, `login  [ needs re-login ]` while its chain is quarantined, `resets  ↺ N banked` while it holds a banked reset, how long ago its usage was read, then whichever of its 5h and 7d bars it reports. A pool account's detail shows `type  shunt`, its family, every provider serving it, its plan, one `status` pill (needs re-login, paused, disabled, or a cooldown with its countdown; none while available), how long ago the listing was read, then whichever of its 5h, 7d and `7d fable` bars the listing reports. While the pool listing cannot be read, or the pool section goes away, a selected pool account gives way to the Usage tab's first row; it comes back once the listing returns, unless since then you moved on the Usage tab, Setup or the Overview, moved the Claude Code account selection on any other tab, or opened the row shown.

## Keys

### Everywhere

| Key | Action |
|-----|--------|
| <kbd>←</kbd> <kbd>→</kbd> (or <kbd>tab</kbd> / <kbd>⇧tab</kbd>) | previous / next tab at the top level; in a descended detail <kbd>←</kbd> returns to the selector and <kbd>→</kbd> does nothing, while <kbd>tab</kbd> / <kbd>⇧tab</kbd> still switch tabs from a read-only detail and do nothing in an editable one |
| <kbd>⌥1</kbd>–<kbd>⌥9</kbd> | jump straight to a tab (<kbd>⌥9</kbd> is always the last); live inside an editor and a descended pane |
| <kbd>↑</kbd> <kbd>↓</kbd> | move the selection through long lists without snapping it to an edge, or scroll a detail pane |
| <kbd>pgup</kbd> <kbd>pgdn</kbd> | move a page in a scrollable list, detail, form or dialog |
| <kbd>⏎</kbd> | act on the selected row (see below) |
| <kbd>n</kbd> | new account (on the Overview, the form's `type` is preset from the row under the cursor; a suspended form comes back as you left it) · on a Claude Code row of the Usage tab: edit the account's note; nothing on a codex or pool row there |
| <kbd>d</kbd> | open the divergence resolver, when one is pending |
| <kbd>x</kbd> | dismiss the oldest toast, then the footer alert; over an open dialog it dismisses the oldest toast only; while a field is open for editing, <kbd>x</kbd> stays with it. Any <kbd>x</kbd> also cancels a pending quit and clears its alert (never the `saving …` line) |
| <kbd>a</kbd> | action menu for the current row |
| <kbd>?</kbd> | keybinding help for this tab |
| <kbd>esc</kbd> | step back out of a sub-pane; in an open text field, put back the saved value (the footer reads `esc revert`), or on the new-account form keep what you typed (`esc done`) |
| <kbd>q</kbd> | step back, or arm quit at the top level; press again to confirm (over changed work the second press opens the loss warning) |
| <kbd>ctrl</kbd>+<kbd>c</kbd> | arm quit from anywhere; press again to confirm (over changed work the second press opens the loss warning) |

A descended Usage or Tokens model detail scrolls one line with <kbd>↑</kbd> / <kbd>↓</kbd>; <kbd>esc</kbd> or <kbd>←</kbd> returns to its selector without changing the selected account or model. <kbd>pgup</kbd> / <kbd>pgdn</kbd> move one page, the visible height less one line: a list or form moves its selection about a page and stops at the first or last row, and no line is passed over unseen. An open text field whose value runs past its row scrolls sideways with the caret, keeping the character you are on whole in view, and the usage tab's note editor does the same with a line wider than it. Choice dialogs and action menus follow the selected option so it remains visible; an overflowing choice shows a scrollbar. A custom-field overwrite whose consequence cannot fit in the choice dialog opens a confirmation with its full explanation scrollable (<kbd>↑</kbd> / <kbd>↓</kbd> and the page keys, while <kbd>←</kbd> / <kbd>→</kbd> pick the button) and cancel selected by default; a fitting choice acts at once. Toasts stack in the top-right corner, at most three lines each: a longer message ends its third line in `…`, and a failure leads with what went wrong and why.

A switch away from an open edit whose typed value differs from the one it opened from — a Setup account field, the `+ new` form, a Fallback or Config field, the herdr tag field, a shunt field or `+ add <kind>` draft, or the Usage note editor — opens a `WARNING` dialog instead of switching: `go back · discard · save`, with `save` selected. `save` checks every changed value first and, if they all pass, commits each and performs the switch (or quit); if any is refused, none is committed, the dialog closes, and the failing item's own `↵` runs — a shunt field or `+ add` draft shows its red `└` line, a rename or env key toasts its reason, and a refused `shunt check` fills the card's `check output` line. A save holding a shunt edit (a changed field or a typed `+ add` draft) beside any other changed work commits the other instant edits and opens the first shunt edit owning the keys — a field keeps its editor, a draft's open field lands in the draft, focus on its `save <kind>` row. A lone shunt edit saves and holds the switch (or quit), proceeding on landing and staying open with its red `└` line on refusal. A shunt field or `+ add` draft whose own save is still checking is not changed work: a switch, quit or jump over it alone holds with no warning and proceeds (or warns) when the save lands; beside other changed work the warning opens at once and its `save` waits for it, re-running over the items still changed if nothing else changed, else (or on a refusal) reopening the warning over everything still changed, and its switch `discard` switches and lets the save land while its quit `discard` holds until the save lands, then quits or warns. A field or `+ add` save in flight holds the quit and warns over its red item on refusal. A quit over any other running shunt save, card write (adopt, move stores, admin key or table, stop/start) or pool remove is final: other keys do nothing beyond dropping a half-pressed second quit (a lone <kbd>ctrl</kbd>+<kbd>c</kbd>, or <kbd>q</kbd> at the top level), and the TUI exits once the write finishes, however it lands. A quit while an account is saving a refreshed login (a claude or codex token rotation, a rolling token's re-stamp, or an account switch) waits the same way, the footer naming that account, and exits once that save ends, however it lands; a usage read never holds a quit, though a refresh that must first rotate the account's token waits for that rotation. During any of these waits the footer reads `saving … · ⌃c ⌃c quit now`; a second quit exits at once, after at most 2 s more for a running token spend. The `require client tokens` restart wait is dropped by an exit; the next `f` asks again. A changed value whose `↵` would open a further dialog (an env-key collision, a shunt rename cascade, or a bind restart) stops the save the same way and opens that dialog. `save` over a mix that includes the `+ new` form commits the saveable rest, then reopens the two-button `discard them and switch?` dialog. `discard` drops the work as `esc` would and performs the switch (or quit); `go back` (or `esc`) closes the dialog and keeps the edit, text and caret intact. The `+ new` form has nothing to save, so it warns with `go back · discard`, `go back` selected. A quit — a second <kbd>q</kbd> at the top level or a second <kbd>ctrl</kbd>+<kbd>c</kbd> from anywhere — over changed work opens the same dialog in its quit form (`save them before quitting?`), and a second <kbd>ctrl</kbd>+<kbd>c</kbd> over a switch's warning turns it to the quit form; over a quit's warning it does nothing more, and over a switch or jump already held on a checking save it turns the hold into a quit, the landing quitting (or warning over what is still changed). An unchanged open edit suspends silently and re-seeds from a newer saved value on return, caret at the end.

On the Tokens dashboard, <kbd>↑</kbd> / <kbd>↓</kbd> move focus card to card in reading order (wrapping), <kbd>pgup</kbd> / <kbd>pgdn</kbd> move about a page and stop at the ends, and the grid scrolls by whole cards when it is taller than the screen: a card that does not fit whole moves below the fold, with a scrollbar at the grid's right edge, instead of clipping its border.

### Tab-dependent

| Key | Behavior |
|-----|----------|
| <kbd>r</kbd> | Usage: refresh the selected Claude Code account only; on a pool row, read the pool listing again; nothing on a codex row, which refreshes on the refresh interval alone. Tokens / Status / Services: reload that tab's data. Everywhere else: refresh every Claude Code account |
| <kbd>t</kbd> | Tokens: cycle the period lens. Everywhere else: force-rotate every Claude Code account's token, after a confirm |
| <kbd>⏎</kbd> | Overview: switch to the selected Claude Code account; inert on a codex or pool row. Usage: descend into the selected account's detail to scroll its full breakdown. Tokens: open the model breakdown, then descend into the selected model's detail; a view with no model has no detail to open. Setup / Fallback: open a detail row, or commit an edit; on Setup's `type` and `family` cycle rows ⏎ mirrors `space`; on a Fallback card's `preferred days` row, open the day picker. Status / Services: open the detail (the `delegates` detail only while it lists a job); in a Services detail, open the confirm of a focused `f` line (on the `shunt` card also: flip a focused `enabled` row, open a focused `check output`) |
| <kbd>⇧↑</kbd> <kbd>⇧↓</kbd> | Overview: reorder Claude Code accounts; inert on a codex or pool row. Fallback (chain focus): reorder chain members |
| <kbd>space</kbd> | Config: cycle a value or flip a toggle. Setup: cycle the `model` row and the `+ new` form's `type` / `family`, flip `auto-start`, open the `alert at` editor; a Setup action row (log in, delete, disable) acts on <kbd>⏎</kbd> alone. Fallback: flip toggle rows and open the typed editors, never the `remove` row. Fallback `preferred days`: step `never` → `weekdays` → `weekends` → `every day` and back to `never`, saving each step; a custom set is one more stop after `every day` until you leave the card. Services `shunt` card: flip a focused `enabled` row, expand or collapse a config entry, step a cycle field; its action rows (`check output`, `+ add <kind>`, `save <kind>`, `remove <kind>`, `+ add token`, a token's `remove`) and its `f` lines act on <kbd>⏎</kbd> alone |
| <kbd>+</kbd> <kbd>-</kbd> | Fallback detail: step `rotate at` or `weekly at` by 5; Setup: step `alert at` by 5 |
| <kbd>e</kbd> | Usage: toggle burn estimates |
| <kbd>p</kbd> | Usage: toggle the ideal-pace marker |
| <kbd>c</kbd> | Overview: cycle the harness filter (all → claude → codex → shunt → all; the accounts panel title names the active one) and return to the row last chosen with the cursor keys, or the first row when the view no longer shows it. Tokens: count cache reads and writes in the token totals |
| <kbd>f</kbd> | Services: move to the selected row's next `f` line, descending from the list onto its first and wrapping after its last; it never applies a fix, <kbd>⏎</kbd> on the focused line does |

The day picker on a Fallback card's `preferred days` row shows each weekday as `[x]` or `[ ]`: <kbd>←</kbd> <kbd>→</kbd> walk the days (and do not switch tabs while it is open), <kbd>space</kbd> toggles the day and saves at once, <kbd>⏎</kbd>, <kbd>esc</kbd> or <kbd>q</kbd> leave it, and <kbd>↑</kbd> <kbd>↓</kbd> leave it and move to the row above or below. <kbd>?</kbd> and <kbd>x</kbd> keep working while it is open; every other key does nothing until you leave, except <kbd>⌥1</kbd>–<kbd>⌥9</kbd>, which still jump to a tab and suspend the picker.

On macOS, <kbd>t</kbd> skips any account holding a live `clauth start` session or an unfinished background job holding the rotating login: that session's login lives in a Keychain item clauth cannot write, so rotating it would sign the session out. An account a background `--with-fallback` session has moved off is not skipped, since the session no longer reads that login.

The footer labels <kbd>c</kbd> `harness` on the Overview; the <kbd>?</kbd> help for that tab does not list it. With the Overview showing codex rows alone, <kbd>↑</kbd> and <kbd>↓</kbd> select codex accounts and the scrollbar follows; <kbd>⇧↑</kbd>, <kbd>⇧↓</kbd> and <kbd>⏎</kbd> do not change a Claude Code account, and <kbd>a</kbd> opens tab-wide entries alone. <kbd>r</kbd> and <kbd>t</kbd> keep working on the Claude Code accounts; <kbd>n</kbd> opens a fresh new-account form with `type  codex`. Neither refresh nor rotation reaches a codex row (codex usage polls on the refresh interval alone, and a codex chain rotates only in the background). On every other tab <kbd>c</kbd> keeps its own meaning or none.

## Action menus

<kbd>a</kbd> opens the actions available for whatever is selected. It lists what no key already does, so on Config, Fallback and Services, where every action already has a key, it holds only the daemon and shunt entries every tab ends on. The footer only advertises <kbd>a</kbd> where something would open.

Entries above the rule act on the account named in the menu's title bar; entries below it act on the tab, and the daemon and shunt entries, when shown, come last.

| Tab | Account | Tab-wide |
|-----|---------|----------|
| Overview | `refresh usage`, `rotate access token`, `disable account` / `enable account`, `open provider console` | `refresh all accounts`, `new account` |
| Usage | `refresh usage`, `rotate access token`, `disable account` / `enable account`, `open provider console` (a pool row: see below; none on a codex row) | `refresh all accounts`, `toggle estimates`, `toggle pace marker` |
| Tokens | none | `period: lifetime` / `daily` / `weekly` / `monthly`, `show all models` / `show claude models` / `show other models`, `toggle cache counting`, `reload stats` |
| Setup | `duplicate account`, `save as preset`, `apply preset`, `open provider console` (none on a codex or pool row) | none |
| Status | none | `refresh status`, `open in browser` |
| every tab | none | `start daemon` / `stop daemon`, then `start shunt` / `stop shunt`, last |

On a shunt pool row, on the Overview or the Usage tab, the menu holds `refresh` (claude and antigravity accounts; shunt has no codex refresh) and `remove` (behind a `remove <name>?` confirm); a kimi row, or one whose sign-in kind clauth does not know, carries no action. One pool action runs at a time, and picking a second while one runs says to wait. An account entry always acts on the account the menu was opened for: if that account is deleted or renamed before you pick, or leaves the pool listing (or the listing cannot be read at that moment), nothing runs and a toast says the account is gone.

The Usage tab claims <kbd>n</kbd> on a Claude Code row for the selected account's note: a free-form text block shown in full on the tab under `notes:` (`press n to add notes` while the account has none). <kbd>⏎</kbd> saves, <kbd>esc</kbd> cancels, <kbd>⌃j</kbd> starts a new line. The note is stored as `profiles/<name>/note.txt` (see [Configuration](Configuration#storage-layout)), so it follows the account on rename and goes with it on delete. <kbd>n</kbd> does nothing on a codex or pool row of the Usage tab; everywhere else it still starts a new account.

`start daemon` shows while no daemon runs and, once you confirm, starts `clauth daemon` in the background, detached from the TUI: it keeps running after you quit the TUI or close its terminal, and writes its log to `~/.clauth/daemon.log`. If a daemon came up elsewhere while the confirm was open, it starts nothing and says `daemon already running`. It starts the plain daemon, so it serves no REST API; for the clauth app, run `clauth daemon --listen` yourself ([Daemon](Daemon)). `stop daemon` shows while one runs and stops it the way `clauth daemon --replace` does, taking the shunt gateway and every enabled proxy down with it (a daemon that takes over at once, such as a standby, runs its own). Neither shows while one of them is still working; a toast reports how it went.

`stop shunt` shows while the daemon runs the shunt gateway and its status is fresh. It asks first, naming how many live sessions run on an account whose base URL points at the gateway when any do and clauth can count them, then holds the gateway off until the daemon next restarts; it never changes the card's `enabled` setting. `start shunt` shows in four cases: with no gateway adopted it opens the Services tab on the `shunt` card, on its `f  adopt config` line when the card offers one; with the gateway disabled it lands on the card's `enabled` row; with no daemon running it asks to start the daemon (hidden while a daemon start or stop is still working); and on a held gateway it lifts the hold. In any other state, and while a shunt action is still working, neither shows. A pick whose entry no longer applies, because the gateway changed since the menu opened, says so and does nothing.

The active period or model filter is omitted from the Tokens menu, so the entries you see are the ones that would change something. `open provider console` follows the same idea from the other direction: it appears only on an account whose endpoint clauth knows a key page for, so an OAuth account's menu is one entry shorter.

The Setup detail pane is itself a list of actions, so <kbd>⏎</kbd> on a row is the action. What the menu adds is what works on the account as a whole, from either the account list or a settings row, and none of it on a codex or pool row (its detail rows carry the actions). On the `+ new` form there is no account to duplicate or save, so its account entry is `apply preset` alone, offered only while `type` is `claude`, stamping the draft's endpoint and model fields.

| Entry | Does |
|-------|------|
| `duplicate account` | asks for a name, then copies every setting onto a new account: endpoint, api key, env, models, thresholds. The stored login stays behind, as do the chain's `preferred` and `last resort` marks, which only one account may hold |
| `save as preset` | stores this account's base url and models under a name you type ([Configuration](Configuration#presets)). An existing preset asks first; a built-in's name is refused |
| `apply preset` | opens the picker, built-ins first. Applying writes what the preset sets and keeps the rest, asking first before it replaces a value; when the account holds a value the preset leaves unset, the confirm offers `keep them` or `clear them` ([Configuration](Configuration#presets)). <kbd>d</kbd> deletes a saved preset |
| `open provider console` | opens the page this account's api key is minted on, in your browser. Only for DeepSeek, Z.ai, OpenRouter, MiniMax and Alibaba Model Studio endpoints, so it is absent on an OAuth account and on any endpoint clauth does not recognise. An Alibaba account gets its own plan's page: Token Plan and Coding Plan are separate products, on separate pages, per console; a Qwen Cloud account gets Qwen Cloud's API Keys page, one page for Individual and Team Token Plan keys |

There is no `remove field` because none is needed: an env row's <kbd>⏎</kbd> edits its value, and an empty value removes the key. Editing it back is the same row.

`disable account` from Overview or Usage asks first, since disabling drops the account from auto-switch, usage polling and status mid-flight; re-enabling is immediate. Neither runs for the active account or for one holding a live `clauth start` session — a Claude Code background job naming one of the profile's runtime trees (launched with `clauth start <p> -- --bg`) counts as a live session, a stopped one too, until `claude rm <id>` (in an `--isolated` session, an unfinished one only), and so does a handed-off `--with-fallback` background session ([Auto-Switch](Auto-Switch)) on every account it has run on; the pick names whichever is in the way.

## Setup tab rows

The list is the Overview's own: Claude Code rows, then a `codex` band, then one `shunt (<provider>)` band per pool provider with a row per account, and `+ new` last; the Overview's `c` harness filter is ignored here. Selecting a Claude Code row opens its settings (rows below); selecting a codex or pool row opens that account's own detail pane. `+ new` turns the pane into the create form, which opens on a `type` row cycling `claude` / `codex` / `shunt`; <kbd>n</kbd> presets the type from the row under the Overview cursor (a pool row → `shunt`, a codex row → `codex`, a claude row → `claude`; with nothing under the cursor the harness filter decides), and from any other tab it opens a claude form; a suspended form comes back exactly as you left it, so the preset applies to a fresh form only. Cycling `type` keeps the name you typed and asks first before it drops a staged login.

The claude form offers `name`, `base url`, `api key` (only once a url is typed), `model`, `+ model override`, `+ login` (only while the base url is empty, minting the OAuth login) and `create account`; after `+ login` (or in its place on an api form), `+ capture current login` stashes the login Claude Code is using now (it appears only while that login exists and no saved account owns it). `create account` saves every field, and a captured login from a different endpoint than the form's takes none of the form's model rows. The codex form offers `name`, `+ login` (codex's own browser login, staged until `create account`), `+ capture current login` (only while your own codex CLI login exists and is uncaptured; it stages that login) and `create account`; `create account` with nothing staged refuses on its own `└` line, and `+ login` and `+ capture current login` refuse a name either roster already holds on the name row, while `create account` refuses a name held by then with a `create failed` toast. The shunt form offers `family` (`claude` / `codex` / `antigravity`), `name` and `+ login`, which is the create: the login modal opens, then the browser opens shunt's authorize URL; once it has, <kbd>r</kbd> opens it again, <kbd>c</kbd> copies it, and <kbd>p</kbd> opens a field where you paste the code the page shows (claude), or the address of the localhost page that fails to load (codex, antigravity); it goes to shunt as typed. `+ login` is disabled, with its reason on its own `└` line, and ignores <kbd>⏎</kbd> while no gateway is adopted, the gateway is not running, the config cannot be read or holds no clauth admin key, or no admin token file exists, except while its own add runs: then <kbd>⏎</kbd> on it reopens the login modal. While another login runs, <kbd>⏎</kbd> on an enabled `+ login` names that login in a toast and starts nothing; a name outside `a-z 0-9 -` refuses on the name row.

A codex account's detail shows `type  codex`, its `plan`, a `login  [ needs re-login ]` pill only while the chain is quarantined, then `re-login` (codex's browser login, as `+ login`; the modal offers <kbd>r</kbd> open again and <kbd>c</kbd> copy link, no paste) and `delete account` (press twice). A pool account's detail shows `type  shunt`, its `family`, its `provider` (` · `-joined when several providers serve it), its `plan`, one `status` pill (`needs re-login`, `paused`, `disabled` or `cooldown`; none while the account is available), then `refresh` (claude and antigravity accounts) and `remove` (press twice; every routed family). A kimi or unknown-mode account shows the facts only.

A saved Claude Code account's rows:

| Row | Sets |
|-----|------|

| `type` | on a saved account, read-only `api` or `oauth`, off the base-url row and tracking what you type into it; on `+ new` it is the `claude` / `codex` / `shunt` cycle that picks the form |

Rolling: `rolling · re-stamps in ~Nh`, `rolling · re-stamp due` inside the last hour, `rolling · no recorded expiry`, and `rolling token stalled` once nothing re-stamped it in time. `mis-filled` is neither: the sidecar holds a rotating pair the split cannot use. The charged states carry the fix beneath them ([Configuration](Configuration#account-types)) |

| `+ login` / `re-login` | what it runs depends on the account, the same three-way split `clauth login` has: an OAuth account mints a browser login, an api-key account re-enters its base url and key inline, and a Model Studio account opens the Alibaba console to capture the usage session its api key cannot stand in for ([Configuration](Configuration#the-alibaba-console-session)). That last one replaces the session and nothing else, since the endpoint and api key keep their own rows. A browser login onto an account that already has an endpoint and a working key leaves both standing too, and replaces the subscription login alone. While a browser login runs its modal offers <kbd>r</kbd> to open the browser again, <kbd>c</kbd> to copy the sign-in link for another device to your local clipboard through the terminal (OSC 52: kitty, WezTerm, Windows Terminal, tmux with `set-clipboard on`, and iTerm2 once `General > Selection > Applications in terminal may access clipboard` is on), and <kbd>p</kbd> to turn that row into a code field: type or paste the code the link's page shows, <kbd>⏎</kbd> submits, <kbd>esc</kbd> brings the row back; a bad paste clears the field and says why |

Appears while ANY long-lived piece exists — the token, the preserved mint backup, or a set `rolling_token` flag — arms on the first press, clears on the second (the full exit: flag, sidecar, and backup together). Faint and inert when clearing would strip the account's last credential; a flag-only account disarms regardless, since no credential is touched |
| `disable account` / `enable account` | hides the account from auto-switch and polling, keeping its files |
| `delete account` | removes the profile; arms on the first press, deletes on the second; with no live session it is refused while a runtime tree still has a background supervisor clauth cannot verify and stop (retry once it has exited, or run `clauth delete <name> --force`) |

## Services tab

Four rows: `shunt`, `delegates`, `plugin`, and `herdr` (shown once herdr resolves; the tab probes for it in the background the first time you open it, and <kbd>r</kbd> probes again). A row's dot carries its health; the full readout lives in the detail pane. <kbd>⏎</kbd> descends into the selected row's detail (the `delegates` detail descends only while it lists a job). A fixable problem shows an `f  <verb>` line under the problem it fixes (the `f` in the blue accent, the verb dim), and its row in the list ends in a blue `f`. <kbd>f</kbd> moves to the selected row's next `f` line (from the list it descends onto the first, and it wraps after the last); <kbd>⏎</kbd> on the focused `f` line opens that fix's confirm, and the footer shows `↵ <verb>` while it is focused. In the `plugin` detail <kbd>↑</kbd>/<kbd>↓</kbd> walk the problems too, the focused one highlighted. In the `plugin` and `herdr` details <kbd>pgup</kbd>/<kbd>pgdn</kbd> scroll diagnostic lines by a page; while reading them, a hidden fix or option cannot act, and an arrow restores action focus. In the `shunt` detail <kbd>↑</kbd>/<kbd>↓</kbd> walk the card's action lines, <kbd>pgup</kbd>/<kbd>pgdn</kbd> scroll it a page and select the first action line in view, <kbd>⏎</kbd> on a focused `f` line opens its confirm, and on the focused `enabled` row <kbd>space</kbd> or <kbd>⏎</kbd> flips it. When `shunt check` refuses an admin fix or a config save clauth made, the card shows a `check output` line: <kbd>⏎</kbd> on it opens the check's output with secrets masked: every value of 8 bytes or more the config could pull in from your environment or from files, then any long key-shaped token still showing.

`shunt` reports the managed gateway (the daemon's live verdict when it runs the gateway, else the gateway record's own) and carries its controls. It names the binary, config and version it resolved, the state and its reason, then the pid and port. With no gateway adopted the state reads `not adopted`, followed by the config shunt would load from where the dashboard runs and a shunt already answering on the address that config sets, each only when there is one; while the card shows that answering shunt, the card checks it again every 5 seconds and drops the line once it stops answering. With no config found the check asks shunt's default address; `SHUNT_SERVER__BIND` moves either, as it moves shunt's own, read from the environment the adopt reads: the running daemon's, else the dashboard's. A daemon that recorded no environment shows `the running daemon recorded no environment; restart it` and offers no adopt. When clauth cannot read the address (a YAML config, a `${...}` reference, port 0, an empty value), a `bind  not read (...)` line says why and the check falls back to shunt's default address; when `SHUNT_SERVER__BIND` hides that the config itself is YAML (a `shunt.toml` linked onto a YAML file counts as YAML), unreadable or not valid TOML, a `config  not read (...)` line says so, and the adopt itself refuses a config that does not parse. A found TOML config that clauth read, with a bind it read, adds an `f  adopt config` line: confirming it takes the config over (a standalone shunt answering on that address refuses the adopt), plans the store move, and writes `~/.clauth/gateway.toml`: with nothing to move and no refusal it adopts `enabled` and a running daemon starts it at once, otherwise it stays off until the move lands or you turn `enabled` on. Once adopted, the card adds the `enabled` toggle, the admin fix, and the codex pool note: `f  add admin key` sits under `admin  clauth's key is not in [server.admin]` when the config has that table but not clauth's key, `f  add admin table` sits under `admin  no [server.admin] table` when it has none (a running gateway restarts once to load it, [Daemon](Daemon)), and `codex  provider <name> needs its own pool login` names each provider with no pool login while the gateway runs healthy with clauth's key (a failed read shows a `pool  <error>` line instead). While the gateway is off and the plan moves a file or refuses, a `MOVE PLAN` section lists `moves` / `stays` rows above `f  move stores in`, which moves the stores in and turns the gateway on, or a single `refused` row saying why no move can run. Descended, <kbd>↑</kbd>/<kbd>↓</kbd> walk the lines a key acts on, landing on each as it scrolls into view; on the focused `enabled` row <kbd>space</kbd> or <kbd>⏎</kbd> flips it, <kbd>f</kbd> moves to the next `f` line, and <kbd>⏎</kbd> on a focused `f` line opens its confirm. Every fix confirms first.

Below its other lines the card lists the adopted config under `SERVER`, `UPSTREAMS`, `MODELS`, `ROUTES` and `CLIENT TOKENS`. `SERVER` holds `bind` and `default_provider`; each upstream, model and route is a `▶` row with a dim summary (an upstream's auth mode and account count, a model's upstream count, a route's `<position>  <model> → <provider>`): <kbd>space</kbd> or <kbd>⏎</kbd> expands its fields in place and folds them again, and <kbd>esc</kbd> on one of its fields folds it back. A key the file leaves unset reads `—`, never shunt's default. On a typed field <kbd>⏎</kbd> opens the editor, <kbd>⏎</kbd> saves and <kbd>esc</kbd> restores the saved value; an emptied field removes its key (`name` and `id` excepted). On a field with a known set of values (an upstream's `provider`, `kind`, `auth mode` and `auth header`, and `service_tier`) <kbd>space</kbd> moves the pick without writing, <kbd>⏎</kbd> saves the pick, and <kbd>⏎</kbd> with no pick pending types any other value. A save runs `shunt check` on the edited copy before it writes: the row shows a spinner and `checking`, then a `✓` (on the new entry's row after an add), and one save runs at a time. clauth's own refusal (a `${...}` bind, a comment the edit cannot place) shows on a red `└` line under the row while you are on it, else as a toast; a refused `shunt check` toasts `save failed` and fills the `check output` line. Saving `bind` on a running gateway asks `restart shunt?` first, since shunt reads it only at start; renaming an upstream or model that other entries name asks first and renames those references in the same write. While the gateway's environment sets `SHUNT_SERVER__BIND`, or its env file cannot be read, the `bind` row is read-only and says why; a legacy `[providers.*]` config lists its providers read-only. Each group ends on `+ add upstream`, `+ add model` or `+ add route` (no `+ add upstream` on a legacy config): it opens blank fields under it and a `save <kind>` row, and nothing is written until that row saves (<kbd>esc</kbd> drops the form). Each expanded entry ends on `remove <kind>`, which asks first (none on an upstream or model whose name another entry shares); removing an upstream that other entries still name is refused by `shunt check`.

The `CLIENT TOKENS` group lists the stored tokens: one row per token (the profile's name and a `remove` chip), the env file's and the daemon env's own client names after them, faint, read-only and labelled `env file` / `daemon env`, then `+ add token`. A failed token-store read shows a faint `tokens  not read` line instead of the rows, a failed read of the unmanaged names keeps the stored rows and shows `other clients  not read`, and an unparsed value shows `<variable>  not parsed`; the first two put the reason on a faint `└` line under them. <kbd>⏎</kbd> on `+ add token` opens the `ADD TOKEN` picker: `+ new profile` first, then every claude profile (one already holding a token ends in a dim `has a token`). Picking a profile opens `point <name> at the shunt gateway?` naming what the overwrite replaces — `it replaces <base> and its current api key.`, `it replaces <base>.`, or, for a subscription login (no base url), `it stops using its subscription login, which stays stored; clear its base url in Setup to go back.` — and `overwrite` mints the token, points the profile at the gateway, and the gateway restarts once. `+ new profile` opens the new-account form with the gateway's base url filled and the api key row read-only (`minted on save`, hint `clauth mints a client token for this profile`): `create account` mints the token under the typed name; capturing a login, editing the url away or cycling `type` off `claude` disarms the mint, and a cancelled form mints nothing. <kbd>⏎</kbd> on a token row confirms `remove <name>'s client token?` / `<name> keeps its api key, which stops working once the gateway restarts.`. With no `[server.auth]` the gateway runs open and the card offers `f  require client tokens`: with any client token (one stored, a client the env file or the daemon env names, or a tokens value clauth cannot read) it confirms `require client tokens?` / `every consumer that sends no token is refused from then on.`, naming the profiles using the gateway; with none anywhere it opens the picker first, then the card reads `require client tokens  waiting for the gateway to restart` and adds `[server.auth]` once the status feed shows a healthy gateway pid other than the one running at the mint.

`delegates` lists the `clauth mcp` job store in its detail. The row's dot reads green while a job runs and dim when none; a recent delegate rate-limit warning names the accounts in its detail. Descended, <kbd>↑</kbd>/<kbd>↓</kbd> walk the jobs (wrapping), <kbd>pgup</kbd>/<kbd>pgdn</kbd> page the list, and the selected job expands under itself into its full facts and run directory; a job's facts include its live `S t/s` while it runs, off its own session, and its own average speed once finished. <kbd>esc</kbd> or <kbd>←</kbd> ascends, <kbd>→</kbd> is inert, and <kbd>tab</kbd> / <kbd>⇧tab</kbd> ascend and switch tabs. The detail binds no stop key: a delegate is stopped through the plugin's `monitor` tool ([Claude Code plugin](Claude-Code-Plugin)).

`plugin` folds the Claude Code wiring checks into one detail: the plugin install record first, then the `mcpServers` entry (`mcp entry` registered or not, `mcp server` ok or won't start, `mcp source`), then the `claude` version, whether `clauth` is on `PATH`, and the clauth data dir. While a live daemon runs a replaced binary, a warning line naming `clauth daemon --replace` closes the detail; it moves no health. Its health is the worst of the four, and two fixes can apply, in this order:

| Verb | When it appears |
|------|-----------------|
| `install plugin` | the plugin reads not installed, installed for this project only, or installed at a version older than this clauth (its `version` line then names both, `0.16.0 (this clauth is 0.17.0)`); installs at user scope, which updates an older install, and turns the plugin on; refuses with a toast while this dashboard's own binary was replaced since it started ([Claude Code plugin](Claude-Code-Plugin)) |
| `wire mcp server` | the `mcpServers` entry is missing, project-local only, or drifted off the current launch line; writes the clauth entry into `~/.claude.json` and the copy in every shared runtime tree under `~/.clauth/profiles/` (isolated trees excluded), leaving a file that already carries it alone. It refuses with a `wire failed` toast carrying one of four lines: `clauth is syncing Claude Code's config; try again in a moment`, `{path} is being written by Claude Code; try again in a moment`, `{path} does not parse as a JSON object; nothing was changed`, `failed to write {path}`; a `~/.clauth` clauth cannot open shows the sync lock's own error instead |

To install the plugin: select the `plugin` row, press <kbd>f</kbd>, then <kbd>⏎</kbd>, and confirm.

The `herdr` row's detail takes focus: <kbd>⏎</kbd> on the row descends, <kbd>↑</kbd>/<kbd>↓</kbd> walk the options rows, <kbd>space</kbd> or <kbd>⏎</kbd> activates one (toggle, cycle, or open the tag-refresh editor), <kbd>+</kbd>/<kbd>-</kbd> step the refresh, <kbd>esc</kbd> closes the editor and then ascends. `delegate row text` opens a confirm that defaults to cancel. When the herdr plugin is installed and its key is unbound or its sidebar row is untemplated, an `f  heal herdr config` line sits above the options: <kbd>↑</kbd>/<kbd>↓</kbd> walk it with them, <kbd>f</kbd> jumps to it, and <kbd>⏎</kbd> on it opens the heal's confirm.
